nrs: from a keystroke to a running generation

What happens on nebula between typing nrs and getting the prompt back: every stage, what it runs as, what it costs, what it prints, how it fails and what state a failure leaves. It ends with a critique of the design and proposals for each stage.

Verified 2026-10-24 on nebula against the source of every component, not against documentation: nh 4.4.2 (crates/nh-nixos/src/nixos.rs, nh-core), Determinate Nix 3.24.0 (Nix 2.35.3), nixpkgs 3ec6363, whose switch-to-configuration-ng has the new user-unit pass, systemd 262, and GRUB with os-prober. The timings come from the journal of the 15:52:05 run: 11.38 s end to end, no package changes.

1. At a glance

nrs is a five-line shell script around nh os switch. nh evaluates and builds the flake as k and prints a package diff. Then it makes three elevated calls:

  1. switch-to-configuration test makes the new generation live.
  2. nix build --profile records it as a numbered generation.
  3. switch-to-configuration boot makes it the GRUB default.

The wrapper ends with a PAM/glibc drift check.

0The wrapper

The mkNhHelper generator in modules/nixos/nh.nix writes three executables (not aliases, so they work in non-interactive shells): nrs (nh os switch), nrb (nh os build, no root) and nrt (nh os test: activate without touching the profile or GRUB). The built nrs:

flake="$(readlink -f "$HOME/src/dotfiles")"
env NH_NO_CHECKS=1 /nix/store/…-nh-4.4.2/bin/nh os switch "$flake" "$@" || exit
pamglibc() { nix-store -q --references "$(nix-store -qR "$1" | grep -m1 -- '-linux-pam-[0-9.]*$')" | grep -E -- '-glibc-[0-9.]+-[0-9]+$'; }
booted="$(pamglibc /run/booted-system)" current="$(pamglibc /run/current-system)"
if [ "$booted" != "$current" ]; then
  echo "warning: PAM glibc changed since boot (${booted#*-glibc-} -> ${current#*-glibc-}): reboot before logging out" >&2
fi
  • readlink -f: ~/src/dotfiles is a convenience symlink, and nix's --flake <path> does not follow a path that is itself a symlink. The flake therefore resolves to git+file:///home/k/src/github/kriswill/dotfiles.
  • "$@" passes through to nh, so nrs -v, nrs --ask, nrs --dry and nrs -- --option … all work.
  • || exit returns nh's status unchanged. The glibc check runs only after a successful switch, so a failed switch reports nothing about the state it left behind (see §12).
  • NH_NO_CHECKS=1: the comment beside it says it skips "the flake's own checks". That is not what it does in nh 4.4.2; see stage 1.

1Pre-flight and target resolution

  • Environment checks. nh's verify_nix_environment requires Nix ≥ 2.31.2, or Lix ≥ 2.93.3. A per-command check_features looks for the experimental features the command needs. NH_NO_CHECKS short-circuits exactly these two functions (nh-core/src/checks.rs). nh os switch never runs nix flake check, so there were never any flake checks to skip.
  • Target. No #attr is given, so nh infers the hostname and builds …#nixosConfigurations.nebula.config.system.build.toplevel.
  • Out-link. The result goes to a temporary directory named nh-os*, which nh deletes on exit. While nh runs, that link is the only GC root holding the new closure.
  • Elevation strategy. auto picks the first of doas, sudo, run0, pkexec, which here is sudo. nh decides now whether it will need it.
  • Specialisation. nh reads /etc/specialisation; nebula has none.

2Evaluation

Cost
5.1 s of wall time and 3.5 GB peak RSS for a full evaluation (nix eval --no-eval-cache …toplevel.drvPath).
Eval cache
Keyed on the locked flake. Once a clean, committed tree has been evaluated, a second nix build of the same attribute returns in 0.03 s. A dirty tree has no lock fingerprint, so every nrs during an edit loop pays the full 5 s.
Source copy
lazy-trees = true (Determinate Nix), so the 656 tracked files (4.9 MB) are not copied into the store before evaluation. Untracked files are invisible to the flake: git add new modules first.
Visible output
Only evaluation warning: lines. That makes this stage the cheapest place to catch a class of mistake before anything changes (P7).

3Realisation

Substituters
hyprland.cachix.org, cache.nixos.org, install.determinate.systems, cache.flakehub.com and edge.cache.flakehub.com. CI (.github/workflows/ci.yml) builds nebula's toplevel on build-relevant PRs and pushes it to the private FlakeHub Cache. Once CI has finished, a change you pushed usually realises entirely from cache.
Expensive misses
Source-only forks: herdr (Rust, from kriswill/herdr), the devenv fork and other pinned flakes. Running nrs before CI has pushed them means building them here.
Negative cache
narinfo-cache-negative-ttl = 3600, and the root daemon does the querying. A miss recorded before CI pushed is remembered for an hour, so another nrs inside that hour builds locally even though the cache now has the path (P11). k is not a trusted user, so a client-side --option cannot override it.
Store
auto-optimise-store = true deduplicates on every write: less disk, slower writes. fallback = true builds from source if a substitute fails. connect-timeout = 15.

4Diff and closure validation

  • dix (nh's nh-diff) compares /run/current-system with the new result: version changes, added and removed packages, closure size. Under the default --diff auto it is skipped if either path is missing.
  • validate_system_closure refuses to activate a result that lacks any of bin/switch-to-configuration, nixos-version, init or sw/bin. NH_NO_VALIDATE bypasses it.
  • No confirmation. nrs does not pass --ask, so the diff scrolls past while nh moves straight on to elevation. Ctrl-C here is the last moment that leaves no trace.

5Elevation

6switch-to-configuration test

This is the stage that changes the running machine. bin/switch-to-configuration is a bash shim that exports OUT, TOPLEVEL, INSTALL_BOOTLOADER, PRE_SWITCH_CHECK and SYSTEMD, then execs the Rust .switch-to-configuration-wrapped (switch-to-configuration-ng). nh runs it with show_output(self.show_activation_logs), which defaults to false. Its stderr is therefore captured. nh prints it only if the program exits non-zero, and loses it entirely if you Ctrl-C. The plan lines it writes ("stopping the following units: …", "restarting the following user units: …") never reach you on a run that hangs.

6.2 The activation script

$out/activate is generated from system.activationScripts, sorted by their deps. On nebula it runs these snippets in this order, all in one bash process. Each snippet records a failure in _localstatus and the script carries on. A bare exit at top level ends the whole script.

The activation script runs at every boot, too. On a running system, a broken snippet only prints an error. At boot it can leave the generation unbootable: in June 2026 a top-level exit 0 skipped everything after it, including the final ln -sfn. Every snippet that can exit is wrapped in a subshell for that reason. A switch exercises the snippets, but it does not test the boot path.

6.3 The user pass

New in this nixpkgs. After the system manager reloads, the system pass asks logind for every user and skips any without /run/user/<uid>. For each remaining user it spawns itself as that uid with a cleared environment and waits for it to finish. The child runs the system pass's unit logic against /etc/systemd/user and that user's manager.

6.4 Start phases, settle and exit codes

Back in the system pass:

  1. sysinit-reactivation.target is restarted.
  2. Reloads, restarts and starts are submitted and waited on. The start phase covers every active target as well as the units stopped in step 6.
  3. The program watches the bus briefly for units that fail or appear.

It then exits with one of three codes:

  • 0: success.
  • 4: a unit failed, or a job could not be submitted. nh reports this as Activation (test) failed.
  • 100: the init interface changed. The new configuration only takes effect after a reboot.

7The system profile

nix build --no-link --profile /nix/var/nix/profiles/system <toplevel> adds system-N-link and repoints system at it. This is the GC root that keeps the generation after nh's temporary out-link disappears. It took 22 ms. nh runs it only if stage 6 succeeded. That is deliberate: a generation that failed to activate never becomes the boot default, at the cost covered in F4.

Retention. nix.gc runs daily with --delete-older-than 7d, so nebula keeps about a week of generations, three today. The rollback window is measured in days, not in generations.

8The bootloader

GRUB is a deliberate choice: nebula went back from systemd-boot to GRUB so that useOSProber could surface Windows on the other disk. The cost is that every switch, even one that changes nothing, runs os-prober as root over foreign filesystems.

9Post-flight

The wrapper finds the glibc that linux-pam links against in /run/booted-system and in /run/current-system. If they differ, it warns. Long-running processes started at boot, such as ly and the lock screen, keep the boot-time glibc. /etc/pam.d switches immediately, so after a glibc bump a logout can fail to log back in until you reboot. This is the only post-condition nrs checks. It runs only on success, and it looks only at PAM.

12. State, interruption and failure modes

A switch changes four things: /run/current-system, the system profile, the GRUB default, and the set of running services. They change at different moments. An interruption or failure leaves them out of step.

13. Case study: the 2026-10-24 hang

The flake update to nixpkgs 3ec6363 brought the user pass. herdr-update-check.service was a oneshot that ends in timeout 12h notify-send -A …. Its unit changed in the update, and it happened to be activating when the switch ran, so the user pass stopped it and queued a start. That start job could finish only when someone clicked a notification. Nothing reached the terminal, because nh had captured stc's output.

Ctrl-C killed the switch after STOP and before START. The second run seeded its plan from the lists on disk and queued the same start against the still-pending job. The fix (commit 69de68a, decision record knowledge/decisions/user-oneshots-skip-switch-restart.md):

  • herdr-update-check became Type=exec with restartIfChanged = false.
  • The three path-triggered capture oneshots (helium, noctalia, gh) also got restartIfChanged = false.
  • The stuck run was stopped by hand.

Three separate weaknesses lined up:

  • a unit design that could sit activating for hours;
  • an upstream wait with no ceiling, placed while services were down;
  • a front-end that hid the one message naming the culprit.

14. Design interrogation

Each finding asks whether a choice holds up under failure, not just on the happy path. The verdicts: sound means keep it, questionable means the trade-off deserves revisiting, flawed means it caused, or will cause, an incident.

F1 · Activation output is hidden by default flawed

switch-to-configuration already prints a plan ("stopping the following units", "restarting the following user units", "NOT restarting …"). nh 4.4.2 captures it unless --show-activation-logs or NH_SHOW_ACTIVATION_LOGS is set, and it shows the capture only on failure. For a batch tool that keeps the screen tidy. For an interactive wrapper whose worst failure is a silent hang, it removes the single best diagnostic, and a Ctrl-C throws it away. On 2026-10-24 that one setting turned a 10-second diagnosis into a debugging session.

F2 · Unbounded waits inside the degraded window flawed (upstream)

block_on_jobs has no deadline. The new user pass runs between the system STOP and START phases, and oneshots default to an infinite start timeout. Together these let any user unit that is slow to finish (a unit you wrote, triggered by a path or a timer) hold system services down for as long as it likes. The system scope protects its own daemon-reload with a 180 s bound but nothing else. Running the user pass after the system START phase would shrink the blast radius to user units, and so would a bounded wait that warns and moves on. The local fix (restartIfChanged = false) deals with the instances we know about, not the class.

F3 · Activation is a child of the terminal questionable

nh runs stc as sudo's child in your terminal's process group. stc ignores SIGHUP, but Ctrl-C (SIGINT) kills it, and a crashed terminal or dropped SSH session takes nh and sudo with it. nixos-rebuild-ng solves this by running stc as a transient unit (systemd-run … --unit=nixos-rebuild-switch-to-configuration, streaming with --wait --verbose --output=cat on systemd ≥ 261). The switch then belongs to PID 1, has one journal identity, and can be stopped deliberately with systemctl stop instead of by accident.

F4 · test, then profile, then boot sound trade-off, poorly surfaced

nixos-rebuild switches in the order profile → bootloader → activate. nh activates first and commits to boot only if activation succeeded, so a configuration that cannot come up cleanly never becomes the default. The price is state B: any exit 4, even a harmless race such as machined.socket on a systemd bump, leaves the machine running a generation that the next reboot will discard. The order is right. What's missing is that nobody tells you which state you are in.

F5 · Resume lists replay silently questionable

Persisting the plan before acting is the correct way to converge after an interrupted switch: the next run restarts what the last one stopped. But the replay is invisible. Your next nrs may bounce sshd, journald and nix-daemon, or re-queue a start that hangs, for reasons that come from an earlier run. Nothing announces it, so it reads as flakiness.

F6 · NH_NO_CHECKS is set for a reason that doesn't exist questionable

The comment says it skips the flake's checks, which rebuild every host. In nh 4.4.2 it skips the Nix version floor and the experimental-feature probe: two fast subprocesses that guard against an nh/nix mismatch. Either fix the comment or drop the variable. An inaccurate rationale beside a setting is how settings outlive their reasons.

F7 · Dotfiles restowed inside root activation sound, sharp edges

Running stowDotfiles as an activation snippet means links self-heal at every boot and every switch without a user session. It is subshell-wrapped and runs as k via setpriv, which also keeps PAM session noise out of the output. The sharp edges: it runs in the boot path (see 6.2), and it hyprctl reloads Hyprland on every switch, even when no link changed.

F8 · os-prober on every switch questionable

Windows does not move, but every nrs pays for rediscovering it. Most of stage 8's 2.37 s is probably os-prober (unmeasured), plus root mounts of the other disk's filesystems on every rebuild. A static chainload entry would produce the same menu item.

F9 · Age-only retention, and GC doesn't rewrite grub.cfg questionable

--delete-older-than 7d deletes generations by age alone. A regression noticed after a quiet week has nothing to roll back to. GC also does not regenerate grub.cfg, so GRUB keeps listing collected generations until the next switch. Booting one of them is exactly how nebula ended up in emergency mode in June.

F10 · Evaluation cost and caching sound

5 s and 3.5 GB is reasonable for a desktop configuration of this size. The eval cache already makes repeat runs on a committed tree almost free. Not worth engineering further.

F11 · Elevation through the 1Password agent sound

Auth is sufficient, so it can never lock you out. The key path is root-owned so it passes StrictModes. One approval covers the three root steps. Nothing to change.

F12 · Post-flight checks only PAM questionable

The glibc check is a good instinct, but it's the only post-condition, and it runs only on success. The questions that matter after a switch go unasked: did a unit fail, does the boot default match what is running, did the kernel change, was an interrupted plan replayed?

The wrapper (P1–P5)

P1–P4 fit in one revision of mkNhHelper.

flake="$(readlink -f "$HOME/src/dotfiles")"

# P3 · an interrupted switch leaves its plan on disk, and this run replays it
for f in /run/nixos/{start,restart,reload}-list "$XDG_RUNTIME_DIR"/nixos/{start,restart,reload}-list; do
  [ -s "$f" ] && echo "nrs: replaying an interrupted plan from $f: $(paste -sd' ' "$f")" >&2
done

# P2 · if activation runs long, name what it is waiting on. Detect it by the
# process, NOT by probing switch-to-configuration.lock: stc takes that lock
# non-blocking, so even a brief probe could make the real switch abort.
( n=0
  while sleep 5; do
    if pgrep -f 'bin/switch-to-configuration (test|boot)' >/dev/null; then n=$((n + 5)); else n=0; fi
    if [ "$n" -ge 45 ] && [ $(( (n - 45) % 30 )) -eq 0 ]; then
      echo "nrs: activation running ${n}s; pending jobs:" >&2
      systemctl list-jobs --no-legend --no-pager >&2
      systemctl --user list-jobs --no-legend --no-pager >&2
    fi
  done ) & watchdog=$!
trap 'kill "$watchdog" 2>/dev/null' EXIT

# P1 · let switch-to-configuration print its plan live
env NH_NO_CHECKS=1 NH_SHOW_ACTIVATION_LOGS=1 nh os switch "$flake" "$@"; status=$?

# P4 · report the state we are in, whether or not nh succeeded
[ "$(readlink -f /run/current-system)" = "$(readlink -f /nix/var/nix/profiles/system)" ] \
  || echo "nrs: the running system is not the boot default; fix the failure, then re-run nrs" >&2
systemctl --failed --no-legend --plain --no-pager >&2
systemctl --user --failed --no-legend --plain --no-pager >&2
[ "$(readlink -f /run/booted-system/kernel)" = "$(readlink -f /run/current-system/kernel)" ] \
  || echo "nrs: new kernel; reboot to run it" >&2
# … existing PAM glibc check …
exit "$status"

P1 · Show the activation plan usability

One environment variable makes stc's own lines visible as they happen. A stall then names its unit ("restarting the following user units: herdr-update-check.service" followed by silence), and nothing is lost on Ctrl-C. It covers stage 6 only; stage 8 stays quiet, which is fine. Cost: a few dozen lines of output per switch.

P2 · Stall watchdog usability resilience

After 45 s of activation, and every 30 s after that, print the pending system and user jobs. Neither needs root. This turns "it's stuck" into "it's waiting on X.service, start job". The detection method matters, and the caveat in the comment is a real hazard: probing the switch lock races stc's non-blocking acquire.

P3 · Announce replays usability

If plan lists exist before nh starts, the previous switch was interrupted. Saying so up front explains the extra restarts. It also warns you that a unit that hung last time is about to be started again.

P4 · Report state on every exit usability

Replacing || exit with a captured status lets the wrapper always report where you stand:

  • a running-versus-boot-default mismatch (state B);
  • failed system and user units;
  • a kernel change that needs a reboot;
  • the existing PAM check.

P5 · Fix the NH_NO_CHECKS rationale resilience

Either replace the comment with the true reason (skip nh's Nix-version and feature probes) or drop the variable and let those probes guard against an incompatible Nix. Dropping it costs two fast subprocesses per run.

Done 2026-10-24: kept the variable and corrected the comment in modules/{nixos,darwin}/nh.nix. In nh 4.4.2 (crates/nh-core/src/checks.rs) the version probe only warns (minimum 2.31.2), and the feature probe checks nix-command and flakes. Both pass on all four machines (Determinate Nix 2.35.3), so skipping them loses no safety net.

Activation (P6–P10)

P7 · Catch the hazard class at evaluation resilience

A short module turns the 2026-10-24 lesson into a build-time warning. It fires for any user oneshot that nothing starts at login (so a path, a timer or a person starts it), that does not stay active, and that a switch would still restart:

{ config, lib, ... }:
{
  warnings = lib.concatLists (lib.mapAttrsToList (name: svc:
    lib.optional (
      (svc.serviceConfig.Type or "simple") == "oneshot"
      && !(svc.serviceConfig.RemainAfterExit or false)
      && svc.restartIfChanged
      && svc.wantedBy == [ ]
    ) "systemd.user.services.${name}: trigger-started oneshot that a switch will restart; set restartIfChanged = false (knowledge/decisions/user-oneshots-skip-switch-restart.md)"
  ) config.systemd.user.services);
}

Warnings print during stage 2, before anything changes. Expect to tune the predicate: upstream-defined user units may trip it.

Done 2026-10-24 (modules/nixos/user-oneshot-check.nix). The predicate also skips disabled units, and accepts RemainAfterExit as a systemd string such as "yes". No unit on nebula trips it, upstream ones included: the only other user oneshots are flatpak-repo and nixos-activation, and both start at login and stay active. It was checked by evaluating with one capture unit's restartIfChanged forced back on, plus a bare test oneshot. The warning named both, and passed over a test oneshot with RemainAfterExit = "yes".

P8 · Put a ceiling on the capture oneshots resilience

Their effective TimeoutStartSec is infinity, which was checked on nebula. serviceConfig.TimeoutStartSec = "2min" on helium, noctalia and gh capture bounds any future hang, such as a git lock or an age prompt, even when something other than a switch starts them.

Done 2026-10-24 (modules/hosts/nebula/users/k/{helium,noctalia}.nix, modules/nixos/git.nix). Normal runs in the journal take 30 s (helium) and 5 s (noctalia), well inside the ceiling. A timeout kills the run and marks the unit failed; the path unit keeps watching.

P10 · Preview the plan usability

switch-to-configuration dry-activate prints "would stop / restart / start the following units" and changes nothing. A nrp helper builds with nh os build, then runs sudo $out/bin/switch-to-configuration dry-activate. It is worth running before risky updates such as a systemd bump or many unit changes.

Correction: this proposal first said dry-activate also previews the user pass. It does not. In switch-to-configuration-ng, do_system_switch exits right after the system plan, before the per-user loop that spawns do_user_switch. That function has a complete dry-run branch, but dry-activate never reaches it, so on its own it never shows a user unit, the kind behind F2.

Done 2026-10-24 as nrs2 --plan instead of a separate nrp. After the build and diff it runs:

  • sudo $out/bin/switch-to-configuration dry-activate for the system units;
  • stc-ng's user pass, dry and as you, started the way stc-ng starts it. This uses an internal interface, so nrs2 says so if the interface moves, and carries on.

Any unit the plan would restart or start while it is activating right now is named in a warning, because the switch would wait for its new run. Tested against a variant build: the user preview showed codebase-memory-mcp's stop and start, and a mid-run test oneshot was flagged. --plan also compares the kernel and PAM against the new build. The decision record is knowledge/decisions/nrs2-plan-user-pass.md.

P6 · Run activation under PID 1 resilience

nh 4.4.2 has no option for this. Two routes:

  • Take over activation in the wrapper. Keep nh for build and diff (nh os build), then perform nh's three root steps yourself, wrapping the first the way nixos-rebuild-ng does:
sudo systemd-run --collect --no-ask-password --quiet --service-type=exec \
  --unit=nrs-switch-to-configuration -E LOCALE_ARCHIVE -E NIXOS_NO_CHECK \
  --wait --verbose --output=cat \
  "$out/bin/switch-to-configuration" test
sudo nix build --no-link --profile /nix/var/nix/profiles/system "$out"
sudo "$out/bin/switch-to-configuration" boot
  • Use nixos-rebuild-ng for the activation half. It already does this, but its order differs (profile first) and you lose nh's diff UX at that step.

A dropped terminal or SSH session then no longer kills a half-applied switch. Check how --wait treats Ctrl-C before relying on it. The aim is that interrupting the switch becomes a deliberate systemctl stop nrs-switch-to-configuration.

P9 · Take F2 upstream resilience

File it against nixpkgs switch-to-configuration-ng with the reproduction: a user oneshot that sleeps, an activating state during the switch, system services held down. Propose one of two changes:

  1. Run the user pass after the system START phase.
  2. Bound block_on_jobs in the user scope, warn, and continue.

Either protects every NixOS user, not only nebula.

Build (P11–P13)

P11 · Forget cache misses sooner performance

nix.settings.narinfo-cache-negative-ttl = 300; (instead of 3600) means an nrs tried before CI finished stops causing local Rust builds after five minutes, not an hour. The cost is more 404 lookups for paths that will never be cached. Measure on the next CI-then-nrs cycle.

Done 2026-10-24 (modules/nixos/determinate.nix). It lands in /etc/nix/nix.custom.conf, which Determinate's nix.conf includes and does not override afterwards. It is nebula only: the Macs' Determinate Nix is outside nix-darwin's control (nix.enable = false), and their nix.custom.conf is empty. Not measured yet.

P12 · Let CI warm the cache for heavy updates performance

For flake updates and fork bumps (herdr, devenv), push first and wait for ci.yml to push nebula's toplevel to FlakeHub Cache. Then nrs pulls instead of compiling. nrb -- --dry-run shows what would be built locally before you commit to waiting.

P13 · Optimise the store periodically performance

Replace auto-optimise-store = true with nix.optimise.automatic = true (weekly) to take hashing and hard-linking off the write path of every build and substitution. It saves the same disk later. The gain is modest; measure a large update before and after.

This produces the same menu without mounting the other disk on every switch. It probably recovers most of stage 8's 2.37 s; confirm with sudo time os-prober first. The memory note about why GRUB came back still holds: GRUB stays, only the probing goes.

P15 · Keep N generations, and refresh GRUB after GC resilience

Status 2026-10-24: not done. Retention is still age-only (snowglobe's nix.gc, 7 days), and GC does not rewrite grub.cfg. nrs2 narrows the gap: every run reads the menu and rewrites it if any listed generation has been collected, so the menu goes stale only between a GC and the next switch. A GC-triggered refresh was tried and dropped after review (see knowledge/decisions/nrs2-boot-menu-check.md).

nix.gc.automatic = false;
programs.nh.clean = { enable = true; extraArgs = "--keep 5 --keep-since 7d"; };
systemd.services.nh-clean.serviceConfig.ExecStartPost =
  "/nix/var/nix/profiles/system/bin/switch-to-configuration boot";

--keep is "at least this many", combined with --keep-since (nh-clean). The ExecStartPost rewrites grub.cfg from the generations that survived, so GRUB can never list a collected generation, which is the June failure. The nh-clean unit name comes from nixpkgs' programs.nh module.

P16 · Make initrd failures debuggable resilience

Already in place; this proposal was a mistake in the report. The harden profile locks root, which on 2026-06-16 left the initrd emergency shell unusable and forced a boot from external media plus nixos-enter. Since then, modules/hosts/nebula/configuration.nix has set boot.initrd.systemd.emergencyAccess = true, which gives passwordless root in the initrd rescue and emergency shell only. A boot failure is already a console session, not a USB stick. A hashed password instead of passwordless is the only open choice. The root fs is unencrypted, so physical access already means full access.

Procedure (P17)

P17 · nrs-status usability

A no-root command that prints:

  • the generation trio (booted, running, boot default) and whether they agree;
  • any leftover plan lists;
  • pending system and user jobs;
  • failed units;
  • kernel and PAM glibc drift since boot;
  • the age of the oldest surviving generation, which is your rollback window.

It reuses the P3/P4 snippets and answers "is this machine in a consistent state?" in one look. That was the first question on 2026-10-24.

Done 2026-10-24 as nrs2 --status. It builds nothing and needs no root. It prints everything above, and also warns when a detached nrs2-switch-to-configuration.service is still running. It ends with ✔ consistent, or a count of what needs attention and exit 1. On darwin it covers the running system, the boot default and the generations. Its first run on nebula caught a real pending job: helium-config-capture was in its 30 s debounce.

Suggested order. P1 and P8 today (four lines, the biggest drop in risk), then P7 and P3/P4. P15 and P14 at the next maintenance window. P6 when the wrapper is being reworked anyway. File P9 regardless; it costs nothing and helps everyone.

Prototyped as nrs2 (2026-10-24, pkgs/nrs2.{nix,sh}, installed by modules/{nixos,darwin}/nrs2.nix) beside nrs, on every host. It covers P1–P4 and P6 without nh: nom build, dix, then switch-to-configuration test as nrs2-switch-to-configuration.service via systemd-run --wait --verbose --output=cat, then the profile and boot. Those last two are skipped when GRUB's menu already boots this build and lists no collected generation. nrs2 reads grub.cfg under its sudo to decide; --boot forces them.

The P6 open question is settled, by testing on nebula: Ctrl-C makes systemd-run exit 130 while the unit runs on to completion. An interrupt therefore detaches instead of killing the switch.

On the Macs it does what nh darwin switch does: set the profile, then run the new generation's own darwin-rebuild activate, with output streamed and the same state report. There is no detach on the Macs, because launchd has no systemd-run here.

Modes:

  • nrs2 --dry builds and diffs without root.
  • nrs2 --test skips the profile and boot entry on NixOS; on darwin it runs darwin-rebuild check.
  • nrs2 --plan previews the switch (P10). On darwin it acts as --dry.
  • nrs2 --status is the no-root consistency check (P17).

The modes are mutually exclusive. --boot warns wherever it does nothing.
