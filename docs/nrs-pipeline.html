nrs: the rebuild helper

The manual for nrs, nrb and nrt, the one script that builds and switches nebula (NixOS) and the Macs (nix-darwin). It covers what each command and mode does, the order of every stage, what the output means, the machinery around it that keeps switching safe, and what to do when something looks wrong.

Verified 2026-10-24 against pkgs/nrs.sh as of commit b95c62b, and by running it: on nebula (NixOS, nixpkgs 3ec6363, Determinate Nix 3.24.0 / Nix 2.35.3, systemd 262, GRUB) and on k (nix-darwin bb0b90d). nrs replaced nh that day. Until then it ran beside nh as nrs2. The analysis that led to it, the earlier version of this document, is in git: git show b95c62b:docs/nrs-pipeline.html. Its finding and proposal numbers (F1–F12, P1–P17) still appear in code comments; §10 maps them. The same manual for browsing on GitHub, with theme-aware diagrams: nrs-pipeline.md. After changing a diagram here, re-export them with bun docs/nrs-pipeline/export-svgs.ts.

1. Commands at a glance

Run all of these as yourself, never under sudo. nrs builds as you and asks sudo only for the root steps, which the 1Password agent approves. Under sudo it refuses with exit 2.

CommandWhat it doesRoot stepOS
nrsBuild, diff, validate, activate, make it the boot default, report.yesboth
nrb
= nrs --dry		Build, diff and validate only. The report compares the kernel and PAM against the new build.noboth
nrt
= nrs --test		NixOS: activate without touching the profile or GRUB. darwin: run the new build's system.checks; nothing is activated.yesboth
nrs --planPreview the switch and change nothing: dry-activate for system units, plus the user units it skips. Flags units the switch would restart while they're mid-run.yesNixOS (darwin: acts as --dry)
nrs --statusNo build, no root: is the machine consistent? Exits 1 if anything needs attention.noboth
nrs --bootSwitch, and rewrite the boot menu even when it's already current.yesNixOS
  • Modes don't combine. --dry, --test, --plan and --status are mutually exclusive (exit 2). --boot warns and is ignored with any mode, and on darwin.
  • Extra arguments go to nix build, for example nrs -L or nrb --show-trace. --status takes none (exit 2).
  • The flake is ~/src/dotfiles, resolved with readlink -f: nix's --flake <path> doesn't follow a path that is itself a symlink, as it is on nebula. The host is uname -n on NixOS and scutil --get LocalHostName on darwin, as nh and darwin-rebuild use.

2. The pipeline and its modes

Every run walks the same stages in the same order, the order nh used. The modes are early exits from that one path. Blue stages run as you; purple ones are the root steps behind sudo.

3. Stage by stage

1Build

nom build "$flake#$attr" --out-link $tmp/result "$@", as you, with nom's live build tree. The attribute is nixosConfigurations.<host>.config.system.build.toplevel, or darwinConfigurations.<host>…. The out-link in a private temp directory is the only GC root for the new closure until the profile is set; it goes away when nrs exits.

Before the build, on NixOS, any resume lists an interrupted switch left in /run/nixos/ or /run/user/$UID/nixos/ are announced, so the replay this run will do is no surprise.

2Diff

dix /run/current-system $out: the package-level changes, path count, size and size delta. If dix fails, nrs warns and carries on.

3Validate

The build must contain its essentials, or nrs refuses to activate it: bin/switch-to-configuration, nixos-version, init and sw/bin on NixOS; activate and sw/bin/darwin-rebuild on darwin. nrb stops here and reports.

4Authenticate

sudo -v once, up front, so a 1Password approval prompt doesn't interrupt the activation output. Sudo authenticates through the 1Password SSH agent (pam_ssh_agent_auth, auth-sufficient), and its timestamp covers every root step that follows.

5Activate, NixOS

switch-to-configuration test runs as a transient systemd unit, the way nixos-rebuild-ng does it:

sudo systemd-run --collect --no-ask-password --quiet --service-type=exec \
  --unit=nrs-switch-to-configuration --wait --verbose --output=cat \
  [-E LOCALE_ARCHIVE=…] [-E NIXOS_NO_CHECK=…] \
  $out/bin/switch-to-configuration test 2>&1 | render_activity
  • Detach, not kill. Ctrl-C ends systemd-run (exit 130), and the switch runs on to completion under PID 1. A lost terminal does the same. nrs prints how to follow it (journalctl -fu nrs-switch-to-configuration) or stop it, reports, and exits 130. Re-run nrs afterwards to set the profile and boot entry.
  • One at a time. stc takes its lock non-blocking, so if the unit from an earlier run is still active, nrs refuses to start another (exit 1).
  • Watchdog. After 45 s of activation, and every 30 s after, it prints the pending system and user jobs. A stall names its unit instead of going silent. It never probes stc's lock, since that could make the real switch abort.
  • Exit codes. 0: carry on. 100: the init interface changed and nothing was activated; nrs warns and still makes it the boot default, so a reboot brings it up. 4: activation finished but a unit failed; the profile and boot entry stay on the old generation, the same rule nh had. Anything else: the same, with that code.

Inside the unit, stc-ng works in this order. Your output shows each step as it happens.

5Activate, darwin

The order nh used: set the profile first, then run the new generation's own darwin-rebuild activate under sudo -H. That script sets HOME, PATH and NIX_REMOTE for root, and handles any legacy activate-user. There's no detach: launchd has nothing like systemd-run wired in, so Ctrl-C interrupts activation as it did under nh. Because the profile is already set, a failed activation means "fix it and re-run nrs".

6Boot step, NixOS

After a successful test, nrs makes the build the boot default: it sets the system profile (nix build --profile /nix/var/nix/profiles/system), then runs switch-to-configuration boot with NIXOS_NO_CHECK=1, because the pre-switch checks already ran in test. It skips both when GRUB's own menu says there's nothing to do. nrt never gets here.

7Report

Every exit ends with the state report, including failures, detaches and every mode:

booted · running · boot default
As generations (gen N), or a bare store name when no generation points at the build. If running ≠ boot default, it warns that a reboot would come back on the default. darwin keeps no /run/booted-system, so it shows two lines.
generations
--status only: how many there are, their range, and the oldest one's age, which is your rollback window.
detached unit · pending jobs
--status only, NixOS: a still-running nrs-switch-to-configuration, and queued system and user jobs.
plan lists
NixOS: resume lists left by an interrupted switch; the next run replays them.
failed units
NixOS: system and user.
kernel
NixOS: what a reboot would change. That means version, toolchain and .config (the new kernel's are read from its bzImage), kernel parameters, and the extra module packages. The running kernel describes itself through /proc; the new one is unpacked the way extract-ikconfig does it.
PAM glibc
NixOS: if the glibc that linux-pam links differs from the booted system's, reboot before logging out, because ly, started at boot, can't load the new PAM modules.
timings
Per stage: build, diff, auth, plan, activate, check, profile, boot.

--dry and --plan compare the kernel and PAM against the new build: what switching and then rebooting would change. Every other mode compares against the running system.

4. Reading the output

Activation output streams live through a renderer. On a terminal it gets glyphs, colour and an in-place progress line. Without one (piped, logged), the same lines print without colour or animation. Lines the renderer doesn't recognise pass through unchanged.

5. Modes in depth

nrt (--test)

NixOS: the full activation of stage 5, unit and detach included, but no profile and no boot entry, so a reboot returns to the boot default. Use it to try a change you aren't sure should survive a reboot. darwin: checks only, as in the figure above. nix-darwin has no "activate without making it the default".

nrs --plan

A dry run of the switch, after the build and diff, which changes nothing. Use it before risky updates: a systemd bump, or many unit changes.

  1. sudo $out/bin/switch-to-configuration dry-activate prints the system plan, as "would …" lines. It runs the pre-switch checks and the activation snippets that support dry activation, sops among them.
  2. The user step, which dry-activate skips. stc-ng's do_system_switch exits right after the system plan, before the loop that spawns the per-user pass. So nrs runs that pass itself, dry and as you: the new build's real binary, a cleared environment, __NIXOS_SWITCH_TO_CONFIGURATION_PARENT_EXE, TOPLEVEL, OLD_TOPLEVEL and NIXOS_ACTION=dry-activate. In that mode it only reads, and it writes no lists. This is stc-ng's internal interface: if it moves, nrs warns and keeps the system half.
  3. Hazards. Any unit on a "would restart" or "would start" line that is activating right now is named. A start job for a oneshot completes only when the run exits, and the switch waits on it. That was the 2026-10-24 hang.

Then the report, comparing kernel and PAM against the new build, and "plan only: nothing was changed". On darwin there's no dry-activate, so --plan warns and acts as --dry. Decision: knowledge/decisions/nrs-plan-user-pass.md.

nrs --status

No build and no root, so it's safe to run any time, by you or by an agent. It's the report of stage 7 with the status-only checks, ending in ✔ consistent (exit 0) or ⚠ N thing(s) above need attention (exit 1). Real pending jobs show up, such as a Helium capture in its 30 s debounce, and count. On darwin it covers the running system, the boot default and the generations.

--boot

Forces the boot step even when the menu is current, for example after editing GRUB settings by hand. It has no effect with any mode, or on darwin, and says so.

6. What keeps switching safe

nrs is the front end. These modules carry the rest, and each closes a failure that actually happened.

7. Troubleshooting

You seeIt meansDo
Activation goes quiet; after 45 s the watchdog lists pending jobsThe switch is waiting on a job, often a user oneshot mid-runStop the named unit (systemctl --user stop …, no sudo for user units). Ctrl-C detaches safely; follow with journalctl -fu nrs-switch-to-configuration.
nrs-switch-to-configuration.service from an earlier run is still activeA detached activation hasn't finishedFollow it, or sudo systemctl stop nrs-switch-to-configuration, then re-run.

8. Learned behaviours & workarounds

Dated and verified; newest first. Correct an entry in place rather than adding a contradiction.

  • 2026-10-24 · darwin-rebuild check activates on macOS. The activate script's #!/usr/bin/env -i shebang wipes checkActivation (nix-darwin bb0b90d). Never use it as a dry check; nrt runs the check mode directly.
  • 2026-10-24 · dry-activate never shows user units. stc-ng exits before its per-user pass. nrs --plan runs that pass itself.
  • 2026-10-24 · The user step can hold system services down. stc-ng updates user units and waits on their jobs, with no timeout, before restarting the system units it stopped. An activating user oneshot (herdr-update-check waiting on a notification click) hung nrs with NetworkManager down. The guards are in §6.
  • 2026-10-24 · nixos-activation.service is last in the user step by design. stc restarts it explicitly on every switch, after the user units (§3).
  • 2026-10-24 · sops-install-secrets runs twice per activation, once for user secrets before /etc and once after. Each run announces every key, hence the collapsing in the renderer.
  • 2026-10-24 · A GC root directory must be readable by the collector. Nix treats an unreadable directory under gcroots as having no roots ("cannot read potential root"). Any directory under gcroots counts as roots, so temp sets must not linger.
  • 2026-10-24 · nh clean can delete a rolled-back profile's current generation. It removes generation links itself; nix-env refuses to. Pruning uses nix-env.
  • 2026-10-24 · Ctrl-C under systemd-run --wait ends only systemd-run (exit 130); the unit runs on. That's what makes the NixOS detach work.
